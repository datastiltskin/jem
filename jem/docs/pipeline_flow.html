JEM Data Pipeline

How the map gets built

One YAML file per institution, pushed through five steps to become the graph the frontend renders. Source: docs/PIPELINE_FLOW.md and docs/SESSION_WORKFLOW.md.

1

Write the entity

data/entities/**/*.yaml

One file per court, tribunal, or oversight body — appointer, funder, complaint path, sources. Hand-edited, or drafted by the scrape pipeline below.

→
2

Validate

scripts/validate.py --strict

Pydantic schema check across every entity: required fields, valid enums, no placeholder source URLs.

fails → fix YAML, re-run
→
3

Check relationships

scripts/validate_graph_refs.py

Confirms every appointment / appellate / funding relationship points at an entity ID that actually exists.

→
4

Derive scores

scripts/derive.py

Computes independence risk, discretionary power, and structural health from each entity's structural fields — never set by hand.

writes → data/derived/scores.yaml
→
5

Build the graph

scripts/build.py

Merges entities + derived scores + relationships into one artifact. build_safe.sh writes to staging first so a bad build never clobbers production.

writes → graph.json (repo root)
→
6

Render

jem/web/

Vanilla JS + D3 frontend reads graph.json through a symlink and draws the four semantic zoom levels — constellation, backbone, sub-entity, detail card.

↑ optional: scrape pipeline drafts step 1 instead of a human

batch_scrape.py

Pass 1 (author) drafts the entity from allowlisted GoI sources. Pass 2 (skeptic) re-fetches those sources and verifies the draft independently.

run_gate.py

Schema, source-host allowlist, and an L4 institution check reject anything unsupported before it reaches step 2. Failures queue as needs_review.

Standard order end to end: validate → edit → validate → validate_graph_refs → derive → build → commit. Shortcut: ./scripts/safe_pipeline.sh.
